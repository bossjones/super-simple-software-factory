# Copilot Tools, Hooks, Permissions, and Containment

verified_on: 2026-09-14
scope: This page covers how Copilot grants and intercepts actions, and why those controls are not a full containment boundary.

- Copilot CLI's permission model is exposed directly through programmatic flags such as `--allow-tool`, `--deny-tool`, `--allow-url`, `--add-dir`, `--allow-all-tools`, `--allow-all-paths`, and `--allow-all-urls`. GitHub's own automation guidance is to grant only the minimum permissions required for the task; source: the [programmatic reference](https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-programmatic-reference) and [Running GitHub Copilot CLI programmatically](https://docs.github.com/en/copilot/how-tos/copilot-cli/automate-copilot-cli/run-cli-programmatically).
- The Python SDK exposes permission handling per session rather than only through CLI flags. The public README documents `on_permission_request` on both create and resume, and leaves pending permission RPC handling to the consumer when no handler is installed; source: the [Python README](https://github.com/github/copilot-sdk/blob/main/python/README.md).
- Hooks are deterministic interception points, not prompt text. GitHub documents `sessionStart`, `sessionEnd`, `userPromptSubmitted`, `preToolUse`, `postToolUse`, `agentStop`, `subagentStop`, and `errorOccurred`, all configured in JSON and executed synchronously as part of agent flow; source: [About hooks for GitHub Copilot](https://docs.github.com/en/copilot/concepts/agents/hooks).
- `preToolUse` is the strongest built-in hook because it can approve or deny tool execution before the command runs, but hook scripts still run as ordinary shell commands and GitHub warns that they need input validation, shell escaping, timeouts, and careful secret handling; source: [About hooks for GitHub Copilot](https://docs.github.com/en/copilot/concepts/agents/hooks).
- Permissions and hooks do not equal containment. Copilot CLI can load trusted-directory resources and offers local/cloud sandboxes that are still in public preview, so they help reduce risk but are not the repository's final policy boundary; source: [About GitHub Copilot CLI](https://docs.github.com/en/copilot/concepts/agents/copilot-cli/about-copilot-cli) and [Using GitHub Copilot CLI](https://docs.github.com/en/copilot/how-tos/copilot-cli/use-copilot-cli/overview).
- Agent Plugins containment is narrower than runtime sandboxing. The Agent Plugins 1.0 spec requires plugin-relative package paths such as `plugin.json`, `skills/`, and `mcp.json` to stay within the plugin root, and it explicitly says those rules do not sandbox plugin subprocesses or runtime-supplied paths. That means plugin/package safety and repo write safety are different concerns; source: the [Agent Plugins 1.0 specification](https://github.com/agentplugins/agent-plugins-spec/blob/main/spec/1.0.0.md) and [About GitHub Copilot plugins](https://docs.github.com/en/copilot/concepts/agents/about-plugins).
- The current SSSF adapter passes the configured tool list as SDK `available_tools`, returns no result for requests that require managed approval, and approves ordinary SDK permission requests once. It does not install a path-aware `preToolUse` hook or derive repository path decisions from permission-request payloads.
- SSSF therefore keeps its own before/after repository snapshot and rollback enforcement after every turn. Copilot's available tools, approve-once callback, optional hooks, and plugin path containment are capability controls, but none of them guarantees "only these repo paths changed"; the authoritative enforcement seam is documented in [sssf-architecture.md](sssf-architecture.md).
