# Copilot Sessions and Events

verified_on: 2026-09-14
scope: This page covers Copilot session identity, resume semantics, event delivery, idle detection, disconnect, and abort; it does not cover plugin packaging or SSSF envelope parsing.

- There is a real documentation conflict around persistence. The session persistence guide opens by saying session state is in memory by default and becomes resumable "with persistence enabled," but the same guide's quick start says state is automatically persisted and stresses that caller-supplied `session_id` is what makes later resume possible. For this port, treat caller-chosen session IDs plus runtime verification as authoritative, not the ambiguous prose alone; source: [Session resume and persistence](https://github.com/github/copilot-sdk/blob/main/docs/features/session-persistence.md).
- Resume is a first-class lifecycle path, not an SSSF invention. The SDK documents `create_session(..., session_id=...)`, `resume_session(session_id, ...)`, persisted storage under `~/.copilot/session-state/{sessionId}/`, and `disconnect()` as the non-destructive cleanup path that keeps disk state resumable; source: [Session resume and persistence](https://github.com/github/copilot-sdk/blob/main/docs/features/session-persistence.md).
- `send_and_wait()` is only a waiting helper. The public Python source says its `timeout` "controls how long to wait" and "does not abort in-flight agent work," so an SSSF phase deadline must call `session.abort()` explicitly after a timeout instead of assuming the wait helper performed cancellation; source: [`python/copilot/session.py`](https://github.com/github/copilot-sdk/blob/main/python/copilot/session.py).
- Early event loss is a real risk if subscription is late. The streaming guide says a session can emit events before create/resume returns, that `session.idle` and other ephemeral events are not persisted, and that post-hoc message fetches cannot recover those transient startup events. SSSF therefore has to subscribe before work begins and treat ephemeral events as live telemetry rather than durable state; source: [Streaming events](https://github.com/github/copilot-sdk/blob/main/docs/features/streaming-events.md).
- In Python, pass the event handler as `on_event=` to both `create_session()` and `resume_session()`. The SDK registers that callback while the lifecycle request is being established; attaching it with `session.on()` only after the method returns can miss ephemeral startup events; source: [`python/copilot/client.py`](https://github.com/github/copilot-sdk/blob/main/python/copilot/client.py) and [Streaming events](https://github.com/github/copilot-sdk/blob/main/docs/features/streaming-events.md).
- The most important event distinction is persisted versus ephemeral. The SDK documents complete assistant/tool events as persisted and replayable on resume, while deltas, progress updates, and `session.idle` are ephemeral and not replayed. That is why SSSF can retain raw events for diagnosis while still normalizing only durable completion facts into its SQLite trace; source: [Streaming events](https://github.com/github/copilot-sdk/blob/main/docs/features/streaming-events.md).
- `session.idle` is the mechanical completion signal to trust. The streaming guide describes it as the point where the agent has finished processing and is ready for the next message, and the Python session source waits for that event in `send_and_wait()` before considering the turn complete; source: [Streaming events](https://github.com/github/copilot-sdk/blob/main/docs/features/streaming-events.md) and [`python/copilot/session.py`](https://github.com/github/copilot-sdk/blob/main/python/copilot/session.py).
- Default cleanup is intentionally conservative. The persistence guide says sessions have no idle timeout by default, active work is protected from idle cleanup, and `delete_session()` is the irreversible cleanup path when disk state must be removed; source: [Session resume and persistence](https://github.com/github/copilot-sdk/blob/main/docs/features/session-persistence.md).
- Fleet and fork are available in the current SDK repository but remain outside this core port. The official [SDK fleet-mode guide](https://github.com/github/copilot-sdk/blob/main/docs/features/fleet-mode.md) exposes `session.fleet.start` through generated RPC bindings and marks that binding experimental; pin the SDK and CLI if depending on it. The repository also contains an experimental generated [`SessionsForkParams`](https://github.com/github/copilot-sdk/blob/main/java/sdk/src/generated/java/com/github/copilot/generated/rpc/SessionsForkParams.java) surface and fork test snapshots, but no stable high-level Python fork API or dedicated fork guide was verified. Keep both surfaces outside the core ADW path until a pinned release and tests justify depending on them; source: [Session resume and persistence](https://github.com/github/copilot-sdk/blob/main/docs/features/session-persistence.md), [Python README](https://github.com/github/copilot-sdk/blob/main/python/README.md), and [Running tasks in parallel with the `/fleet` command](https://docs.github.com/en/copilot/concepts/agents/copilot-cli/fleet).

Refresh from the persistence guide, streaming guide, and `python/copilot/session.py` before changing timeout handling or event normalization.
