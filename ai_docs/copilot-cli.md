# GitHub Copilot CLI Reference

verified_on: 2026-09-14
scope: This page covers the user-facing Copilot CLI commands and operational diagnostics, not the Python SDK internals.

- Copilot CLI has both an interactive `copilot` interface and a programmatic `copilot -p/--prompt` interface for one-shot automation runs. The GitHub Docs references for that split are [About GitHub Copilot CLI](https://docs.github.com/en/copilot/concepts/agents/copilot-cli/about-copilot-cli), the [CLI command reference](https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-command-reference), the [programmatic reference](https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-programmatic-reference), and [Running GitHub Copilot CLI programmatically](https://docs.github.com/en/copilot/how-tos/copilot-cli/automate-copilot-cli/run-cli-programmatically).
- The minimum non-interactive controls SSSF should reason about are `-p`, `-s`, `--model`, `--no-ask-user`, `--allow-tool`, `--deny-tool`, `--allow-url`, `--add-dir`, and the broader `--allow-all*` switches. GitHub explicitly recommends the narrowest permissions possible for automation instead of defaulting to `--allow-all`; see the [programmatic reference](https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-programmatic-reference) and [programmatic how-to](https://docs.github.com/en/copilot/how-tos/copilot-cli/automate-copilot-cli/run-cli-programmatically).
- The CLI's built-in operational surfaces are worth preserving in documentation because they are the fastest way to inspect what a local installation can do: `copilot help [billing|config|commands|environment|logging|monitoring|permissions|providers|sandbox]`, `copilot version`, `copilot mcp`, `copilot plugin`, `copilot skill`, `copilot instruction`, and `copilot lsp` are all part of the published command set in the [CLI command reference](https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-command-reference).
- Trust and isolation are separate concerns. Copilot CLI asks for trusted-directory approval before loading project resources, and its local/cloud sandboxes are still in public preview, so later tasks must not confuse "trusted workspace" or "sandbox available" with the repository write policy SSSF enforces in code; see [About GitHub Copilot CLI](https://docs.github.com/en/copilot/concepts/agents/copilot-cli/about-copilot-cli) and [Using GitHub Copilot CLI](https://docs.github.com/en/copilot/how-tos/copilot-cli/use-copilot-cli/overview).
- `/review` is documented as an interactive change-review surface and `/fleet` is documented as a parallel subagent fan-out surface. Both are useful operator features, but Task 1 treats them as adjunct CLI behaviors rather than the deterministic ADW core; see [Requesting a code review with GitHub Copilot CLI](https://docs.github.com/en/copilot/how-tos/copilot-cli/use-copilot-cli/agentic-code-review) and [Running tasks in parallel with the `/fleet` command](https://docs.github.com/en/copilot/concepts/agents/copilot-cli/fleet).

Refresh from the GitHub Docs pages above when command names, permission flags, or trust/sandbox behavior matter for later tasks.
